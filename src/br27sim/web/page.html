        CAN bus and data logging

        One CAN 2.0 bus with the dash MCU at the front end and node RL at the rear end, 120 Ω at each. The chain runs dash unit → FR → FL → firewall grommet → a splice beside the EMU → RR → RL; the EMU joins on a ~0.1 m stub with its own terminator off. The other corner nodes sit on short stubs along the way, and the dash MCU reads the IMU and GPS directly and logs them, so they stay off the bus. Every frame is simulated with real arbitration, using the rates from the sample-rate form. The CAN FD layouts stay in the menu as what-ifs.

            Fault codes and CAN priority

            Every node runs the same logic for each code it owns: a condition has to hold for its debounce time before the code goes active, and it has to stay clear for its clear time before it resets. Latching codes stay active until the car is reset. Fault frames get the lowest IDs on the bus, so they win arbitration over all sensor and ECU data.

            Fault to test

            The frame is injected at the busiest moment of the simulated bus, when the most frames are queued, so it has to win arbitration to get through.

                  Where the array looks

                  inner pixelouter pixel

                    Inner / centre / outer averages

                    The tread is split into three equal thirds. Each zone shows the average of the pixels in it, colored by temperature, and its error against the true tread average for that third. The squares on top show which pixels feed each zone (grey: dropped, not on the tread). Fixed map: the logger picks each zone's pixels once with the wheels straight and keeps them, so with the sensor on the chassis the tire turns under the row and the zones read the wrong part of the tread, or the track. Corrected with the steering angle: the logger reads the steering sensor and uses a table of which pixels land in each zone at each angle (made from this geometry or from a calibration sweep), and drops pixels that have left the tread.

                        Mock dash

                        It boots, then goes straight to the dash. MODE (button 1) steps through the driver's displays: Endurance, Check tires, Debug and Autocross, from the driver's dash preferences sheet. CLEAR (button 2) clears a warning. MENU opens CAN data, the fault log, logging, system load, LoRa and settings. In the menu, MODE moves down, MENU selects and CLEAR goes back; you can also tap the screen. A new fault takes the whole screen, even over the menu: a yellow warning for 1.5 s, a red critical fault for up to 8 s. Then, or sooner if you press CLEAR, it moves to the warning box until it goes away. A red fault comes back to the full screen every 15 s while it is still active. Each session is 5 laps, then it starts over. Oil, water, fuel and tire values are mock signals until those sensors are chosen.
